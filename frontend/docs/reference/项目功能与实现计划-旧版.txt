《后来呢？——由未来旅行者回答的地点时间胶囊》
项目功能与实现计划

版本日期：2026-09-22
文档状态：需求讨论稿。已确定内容可直接用于开发；标有“待确认”的内容需要队伍讨论后再定。


一、项目目标

“后来呢？”是一个围绕地点和时间展开的旅行问答产品。

用户可以把一张过去或现在的照片绑定到具体地点，留下一个需要未来旅行者到现场回答的问题，并设置期望回答的时间范围。未来准备前往该地点的旅行者可以领取问题，通过新照片和文字带回现场回答。一个问题允许收到多位旅行者在不同时间提交的多次回答，最终形成地点变化的时间线。

典型案例：
用户今天在景区许愿树上挂下一块许愿牌，创建问题“请一年后路过这里的人帮我看看，它还在吗？”一年后，准备前往该景区的旅行者收到任务，在现场拍摄新照片并提交回答。之后到达该地点的其他旅行者仍可继续回答。


二、比赛交付形式

1. 主要交付一个可以通过网址打开的移动端 H5 网站。
2. 页面优先适配手机浏览器，同时保证电脑浏览器可以正常操作。
3. 评委打开 LIVE DEMO 链接后无需自行注册，可以直接进入演示模式。
4. 同一个演示环境中允许一键切换“提问者”和“旅行者”身份。
5. 准备一套完整的预置案例，确保评委可以在几分钟内体验完整流程。
6. 最终同时准备演示视频，作为现场网络或第三方接口异常时的备用材料。


三、用户角色

1. 提问者
   - 创建地点时间问题。
   - 上传作为参照的旧照片或当前照片。
   - 查看问题的匹配和回答状态。
   - 查看所有旅行者提交的回信。

2. 旅行者
   - 添加自己的未来行程。
   - 查看与行程匹配的“顺路愿望”。
   - 领取想要回答的问题。
   - 上传现场照片和文字回答。
   - 查看自己已经领取和完成的任务。

3. 演示模式
   - 使用预置的提问者和旅行者数据。
   - 顶部始终显示当前身份。
   - 可以一键切换身份，不需要退出或重新登录。
   - 模拟行程、模拟定位等内容必须明确标注，不伪装成携程真实数据。


四、必须实现的功能

功能 1：演示入口与身份切换

1. 首页提供“进入演示”按钮。
2. 进入后默认使用预置的提问者身份。
3. 顶部或个人页提供“切换为旅行者/提问者”入口。
4. 切换身份后，页面数据和可执行操作随角色变化。
5. 身份切换只服务于比赛演示；底层数据仍按不同用户保存。

验收标准：
评委无需注册，可以在一台设备上先发布问题，再切换为旅行者完成回答，最后切回提问者查看回信。


功能 2：创建地点时间问题

提问者需要填写：
1. 问题标题，例如“我的许愿牌一年后还在吗？”
2. 详细描述，说明希望未来旅行者观察什么。
3. 一张参照照片。首版只支持图片，不支持视频和录音。
4. 地点名称和所属城市。
5. 具体 POI，例如景区、车站、街道或店铺。
6. 期望回答的开始日期和结束日期。
7. 可选的拍摄建议，例如“请尽量拍到许愿树和左侧栏杆”。

页面需要提供：
1. 必填项校验。
2. 图片预览和重新选择。
3. 发布前预览。
4. 发布成功反馈。
5. 问题状态展示。

问题状态建议：
草稿、等待匹配、已有旅行者领取、已有回答、已结束。

验收标准：
用户能够创建一条包含图片、地点、问题和回答时间窗的记录，并在问题详情页正确查看。


功能 3：添加未来行程

旅行者可以通过两种方式添加行程：

1. 手动行程
   - 填写目的地城市。
   - 选择一个主要目的地或 POI。
   - 填写到达日期和离开日期。

2. 比赛模拟行程
   - 点击按钮载入预设行程。
   - 预设行程应能够立即匹配到演示问题。
   - 页面明确显示“比赛模拟行程”。

暂不接入携程订单或未来行程 API。目前没有确认存在面向普通开发者、可以读取用户完整携程行程的公开接口。未来产品化时，可以在用户明确授权和数据最小化的前提下预留携程内部能力的适配接口。

验收标准：
旅行者添加或载入行程后，可以立即进入匹配结果页，并看到符合条件的问题。


功能 4：问题与行程匹配

首版采用简单、可解释的规则匹配，不使用机器学习推荐系统。

匹配条件：
1. 问题的回答时间窗与旅行日期存在重叠。
2. 行程城市与问题城市相同。
3. 如果双方都有 POI 或坐标信息，优先推荐距离更近的问题。

排序建议：
1. 具体 POI 相同的任务优先。
2. 距离更近的任务优先。
3. 期望回答时间更接近的任务优先。
4. 尚未收到回答的问题优先。

匹配结果卡片显示：
问题标题、参照照片、地点、期望回答时间、当前回答数量、预计是否顺路。

验收标准：
预置演示行程可以稳定匹配到预置问题；时间或城市不符合的任务不会出现在匹配结果中。


功能 5：领取顺路愿望

1. 旅行者进入任务详情页查看原问题、旧照片、地点和拍摄建议。
2. 点击“我来看看”领取任务。
3. 同一个问题允许多位旅行者领取和回答。
4. 旅行者可以取消尚未完成的领取。
5. 领取任务不会阻止其他旅行者参与。

验收标准：
领取后任务出现在“我的任务”中，提问者可以看到已有旅行者准备回答，但不能看到对方的私人行程信息。


功能 6：提交现场回信

旅行者提交：
1. 一张现场新照片。
2. 一段现场观察或回答文字。
3. “我确认这是本次旅行中现场拍摄的内容”确认项。

首版不强制读取手机定位，也不显示“平台已验证”。页面只显示“旅行者声明现场拍摄”。

图片要求建议：
1. 支持 JPG、JPEG、PNG 和常见手机图片格式。
2. 上传前压缩，建议单图不超过 1MB，长边不超过 1600 像素。
3. 显示上传进度和失败后的重试入口。
4. 禁止把数据库账号、云服务密钥等信息写进图片地址或前端代码。

验收标准：
旅行者能够从任务详情提交图片和文字；提交成功后任务状态更新，提问者可以立即看到新回答。


功能 7：查看全部回答和地点时间线

1. 一个问题允许对应多条回答。
2. 所有回答默认按提交时间从早到晚排列。
3. 每条回答显示新照片、文字、回答者昵称、提交时间和现场声明。
4. 参照照片固定显示在页面上，方便与每次回答对照。
5. 可以切换为“最新回答优先”。
6. 不删除早期回答，新回答追加到时间线中。

验收标准：
同一问题提交两条以上回答后，提问者可以看到完整时间线，并清楚区分不同时间和不同回答者。


功能 8：我的内容

提问者视角：
1. 我发布的问题。
2. 等待回答的问题。
3. 已收到回答的问题。

旅行者视角：
1. 我的未来行程。
2. 已领取任务。
3. 已完成任务。

验收标准：
用户能够从个人页快速返回自己相关的问题、行程和回答，不依赖浏览器返回按钮寻找内容。


五、AI 功能规划

AI 不进入第一阶段开发，先完成不依赖 AI 的核心业务闭环。

第二阶段最小 AI 功能：
1. 输入原问题、参照照片、新照片和旅行者原话。
2. 输出对问题的直接回答。
3. 列出新旧照片中可以观察到的变化。
4. 列出无法确认或可能误判的内容。
5. 将旅行者原话整理成一封有温度的回信。

AI 结果必须：
1. 标注为“AI整理”或“AI观察摘要”。
2. 与原始照片、原始回答同时展示。
3. 不把不确定内容写成事实。
4. AI调用失败时不影响旅行者提交原始回答。
5. 超时后显示“分析中”或“暂时无法生成”，最多自动重试一次。

暂不实现：
1. 自动判断照片是否真实现场拍摄。
2. 自动照片对齐。
3. 差异热力图。
4. 自研或训练视觉模型。


六、页面清单

1. 项目介绍/演示入口页。
2. 首页/问题广场。
3. 身份切换入口。
4. 创建时间问题页。
5. 发布前预览页。
6. 问题详情与回答时间线页。
7. 添加行程页。
8. 模拟行程选择页。
9. 匹配任务列表页。
10. 任务详情与领取页。
11. 提交现场回信页。
12. 提交成功页。
13. 我的内容页。
14. 演示数据重置入口。


七、核心数据对象

1. 用户 User
   - 用户编号
   - 昵称
   - 头像
   - 是否为演示用户
   - 创建时间

2. 时间问题 Question
   - 问题编号
   - 发布者编号
   - 标题
   - 详细问题
   - 参照图片地址
   - 城市和 POI
   - 可选经纬度
   - 回答开始日期
   - 回答结束日期
   - 拍摄建议
   - 状态
   - 创建时间

3. 行程 Trip
   - 行程编号
   - 旅行者编号
   - 城市和目的地
   - 可选 POI 和经纬度
   - 到达日期
   - 离开日期
   - 来源：手动填写或比赛模拟
   - 是否参与任务匹配

4. 任务领取 Claim
   - 领取编号
   - 问题编号
   - 旅行者编号
   - 状态：已领取、已完成、已取消
   - 领取时间

5. 回答 Answer
   - 回答编号
   - 问题编号
   - 领取编号
   - 回答者编号
   - 新照片地址
   - 原始回答文字
   - 是否勾选现场声明
   - 提交时间
   - AI分析状态

6. AI分析 AIAnalysis（第二阶段）
   - 分析编号
   - 回答编号
   - 直接结论
   - 可观察变化
   - 不确定项
   - 整理后的回信
   - 状态：等待、成功、失败
   - 模型版本和创建时间

关系：
一个用户可以发布多个问题。
一个旅行者可以添加多个行程。
一个问题可以被多位旅行者领取。
一个问题可以拥有多个回答。
一个回答最多对应一份 AI 分析结果。


八、后端接口草案

以下是接口职责草案，具体路径可在后端框架确定后调整：

1. 获取问题列表。
2. 创建、编辑和查看问题。
3. 添加和查看旅行行程。
4. 根据行程获取匹配任务。
5. 领取或取消任务。
6. 提交现场回答。
7. 获取一个问题的全部回答。
8. 获取当前演示身份的个人内容。
9. 重置比赛演示数据。
10. 请求或查询 AI 分析结果。

前端不能直接连接 MySQL。若使用 MySQL，必须通过后端 API 访问数据库，数据库账号和密码只保存在后端环境变量中。


九、技术方案当前状态

已经确定：
1. 交付移动端 H5 网站和 LIVE DEMO 链接。
2. 单一演示入口支持提问者与旅行者身份切换。
3. 行程同时支持手动填写和比赛模拟数据。
4. 使用简单规则完成问题匹配。
5. 首版不强制手机定位。
6. 首版只支持图片和文字。
7. 一个问题允许多条回答，所有回答都展示。
8. AI功能不进入第一开发阶段。

待队伍确认：
1. 前端使用 Vue 3、React 还是其他框架。
2. 是否使用 TypeScript。
3. 后端使用 Spring Boot、Express、NestJS、FastAPI 还是其他框架。
4. 是否最终采用 MySQL。
5. 谁负责数据库和后端接口。
6. 前端、后端、数据库和图片最终部署到哪里。
7. 图片使用对象存储还是服务器本地磁盘。
8. 是否实现真实用户登录；建议比赛版先不做。
9. 第二阶段使用哪个多模态视觉模型。


十、明确不进入首版的功能

1. 视频和录音上传。
2. 强制手机定位和轨迹采集。
3. 携程真实订单读取。
4. 原生 Android 或 iOS App。
5. 微信小程序。
6. 机器学习推荐系统。
7. 积分、排行榜和复杂社交系统。
8. 聊天和私信。
9. 自动照片对齐和差异热力图。
10. 支付、打赏和商业化功能。


十一、建议开发阶段

阶段 1：前端演示闭环
1. 创建前端项目和基础页面结构。
2. 使用本地模拟数据实现身份切换。
3. 完成创建问题、添加行程、任务匹配、领取和回答流程。
4. 完成多次回答时间线。

阶段 1 验收：
断开后端后，仍能在一台电脑或手机浏览器完整演示核心故事。

阶段 2：真实后端与数据库
1. 确定后端框架。
2. 建立用户、问题、行程、领取和回答数据表。
3. 实现接口并替换前端模拟数据。
4. 加入图片上传和环境变量管理。

阶段 2 验收：
两台设备访问同一测试地址，可以看到相同的问题和回答数据。

阶段 3：部署和演示稳定性
1. 部署前端、后端、数据库和图片存储。
2. 配置 HTTPS、跨域和环境变量。
3. 加入演示数据初始化与重置。
4. 准备网络失败时的备用数据和演示视频。

阶段 3 验收：
未参与开发的人通过公开链接可以独立完成核心流程。

阶段 4：最小 AI 能力
1. 后端调用多模态视觉模型。
2. 比较新旧照片并生成结构化结果。
3. 保存和展示 AI 整理回信。
4. 实现超时、失败和重试降级。

阶段 4 验收：
AI失败不会阻止原始回答提交；AI成功时能够围绕用户的问题描述新旧照片中可观察到的变化。


十二、核心验收场景

场景 1：发布问题
提问者上传许愿牌照片，绑定地点，设置一年后的回答时间并成功发布。

场景 2：行程匹配
旅行者载入对应城市和日期的模拟行程，系统推荐该许愿牌问题。

场景 3：现场回答
旅行者领取任务，上传新照片和文字，确认现场声明并提交。

场景 4：查看回信
切换回提问者身份，可以立即看到新回答和新旧照片。

场景 5：多次回答
第二位旅行者再次回答同一问题，页面同时显示两次回答，并按时间组成时间线。

场景 6：不匹配情况
城市不同或日期不重叠的行程不会匹配到该任务。

场景 7：异常处理
图片上传失败、后端暂时不可用或AI分析失败时，页面给出明确提示，用户输入不丢失。


十三、首版成功标准

1. 评委通过一个网址即可进入作品。
2. 不阅读说明，也能理解“把问题留在地点，交给未来旅行者回答”的核心概念。
3. 五分钟内可以完成发布、匹配、领取、回答和查看回信。
4. 演示过程不依赖真实携程接口。
5. 所有模拟数据都有明确标识。
6. 多位旅行者可以回答同一个问题。
7. 即使AI功能未完成，核心业务闭环仍可运行。
8. 项目中不包含数据库密码、云服务密钥或个人隐私数据。
