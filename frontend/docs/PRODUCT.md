## 1. 产品目标

“后来呢？”是一个围绕地点和时间展开的旅行问答产品。

用户可以将一张过去或现在的照片绑定到具体地点，留下一个希望未来旅行者回答的问题，并设置期望回答时间窗。后来前往该地点的旅行者可以领取问题，通过现场新照片和文字带回答案。同一个问题允许在不同时间收到多次回答，所有回答共同形成地点时间线。

核心价值不是攻略推荐，而是让旅行者帮助陌生人看见一个地点后来发生了什么。

### 核心案例

用户在景区许愿树上挂下一块许愿牌，创建问题：“以后路过这里的人，可以帮我看看它还在吗？”未来前往该景区的旅行者领取问题，拍摄现场照片并回答。后续其他旅行者仍可继续回答，形成许愿牌和地点变化的时间线。

## 2. 交付形态与用户模型

- 交付一个通过 LIVE DEMO 网址直接打开的移动端 H5。
- 手机浏览器优先，同时保证电脑浏览器能够操作。
- 评委无需注册即可进入演示环境。
- 不设置“提问者”和“旅行者”身份切换；同一用户可以发布问题，也可以回答其他用户的问题。
- 演示环境包含当前演示用户及若干预置用户，数据所有权仍按用户区分。
- 模拟行程、模拟回答和预制图片必须明确标注，不能伪装成携程或真实用户数据。

## 3. 一级导航与页面

底部一级导航为：`发现 / 行程 / 发布 / 我的`。

| 发现 | 浏览全国策展问题；有行程后切换行程匹配模式 |
| 创建问题 | 填写问题、参照照片、地点、时间窗和拍摄建议 |

## 4. 核心功能需求

### 4.1 发现与行程匹配

- **FR-01**：未设置有效行程时，发现区展示固定策展顺序的全国问题流。
- **FR-02**：未设置有效行程时，“匹配行程”按钮处于禁用状态，并说明需要先添加行程。
- **FR-03**：用户可以手动添加未来行程，包含目的地城市、主要 POI、到达日期和离开日期；添加页提供返回行程列表的入口。
- **FR-04**：用户可以主动载入一条明确标注为“比赛模拟行程”的预置行程。
- **FR-05**：设置当前行程后，“匹配行程”按钮启用；点击后发现区只展示符合该行程的问题。
- **FR-06**：全国发现流和匹配结果都使用单列图片卡片，一屏约展示一至两张卡片。
- **FR-07**：发现内容的顺序在同一数据版本下保持稳定，不使用每次刷新都会改变的随机排序。

### 4.2 创建地点时间问题

- **FR-08**：用户可以填写标题、详细问题、参照照片、地点、回答开始日期、回答结束日期和可选拍摄建议。
- **FR-09**：标题、详细问题、参照照片、城市、POI 和回答时间窗为必填项。
- **FR-10**：开始日期不得晚于结束日期，发布前显示明确的字段校验错误。
- **FR-11**：参照照片支持预览和重新选择。
- **FR-12**：用户必须经过发布预览确认后才能正式发布。
- **FR-13**：发布成功的问题立即出现在“我的问题”和对应的公开内容中；发布完成页的“返回”进入“我的问题”。

### 4.3 领取和回答

- **FR-14**：用户可以查看其他用户问题的参照照片、地点、回答时间窗和拍摄建议。
- **FR-15**：用户可以点击“我去看看”领取问题；领取不会阻止其他用户继续领取。
- **FR-16**：用户可以取消尚未完成的领取。
- **FR-17**：已领取问题出现在“我的任务”中。
- **FR-18**：提交回答必须包含一张现场新照片、一段文字和已勾选的现场拍摄声明。
- **FR-19**：首版只显示“旅行者声明现场拍摄”，不能宣称平台已经验证真实性。
- **FR-20**：演示时可填入预制回答，也可完全自行填写或在预制回答上修改。
- **FR-21**：提交成功后，回答立即加入问题时间线，且刷新页面后仍然存在。

### 4.4 回答时间线与满意回答

- **FR-22**：一个问题允许多位用户领取，并允许存在多条回答。
- **FR-23**：时间线默认按提交时间从早到晚排列，并允许切换为最新回答优先。
- **FR-24**：每条回答显示新照片、文字、回答者昵称、提交时间和现场声明。
- **FR-25**：参照照片在详情中保持可见，方便与每次回答对照。
- **FR-26**：问题发起者可以将任意回答标记或取消标记为满意回答。
- **FR-27**：同一问题允许有多条满意回答；标记满意不会关闭问题，也不会隐藏其他回答。
- **FR-28**：非问题发起者不能看到或执行满意回答操作。

### 4.5 我的内容与演示控制

- **FR-29**：“我的”按照我的问题、我的行程、已领取任务和已完成回答组织内容。
- **FR-30**：用户不依赖浏览器返回按钮即可回到自己的内容。
- **FR-31**：演示数据可以通过明确的重置入口恢复到固定初始状态。
- **FR-32**：重置操作必须二次确认，并说明会清除当前浏览器中的演示修改。

演示数据初始化失败时，显示可理解的错误和重试入口，不展示尚未初始化的正常页面。

## 5. 业务规则

### 5.1 匹配资格

问题进入某个行程的匹配结果，必须同时满足：

1. 问题城市代码与行程城市代码相同；
2. 问题回答时间窗与行程日期存在重叠。

排序规则及坐标缺失处理以 [TECHNICAL.md](TECHNICAL.md#匹配算法) 为准。

### 5.2 问题展示状态

状态不由用户手工修改，按回答动态计算：

1. 存在至少一条满意回答：`有满意回答`；
2. 否则存在至少一条回答：`有回答`；
3. 否则：`无回答`。

领取人数单独显示为“有 N 人准备前往”，不属于问题状态。

### 5.3 数据可见性

- 问题及公开回答对演示环境用户可见。
- 旅行者的私人行程详情不能展示给问题发起者。
- 问题发起者只看到领取人数和公开回答。
- 当前用户不能领取自己发布的问题。

## 6. 预制故事与未来回信

第一阶段只制作一套可完整演示的预制故事。

- **FR-33**：选择预制问题后，可以修改标题、详细问题、回答时间窗和拍摄建议。
- **FR-34**：预制故事的地点和参照照片锁定，避免未来回答与场景不一致。
- **FR-35**：预制问题发布成功后，不自动伪造实时回答；用户主动点击“预览未来回信”。
- **FR-36**：按钮文案根据所选时间窗动态生成，例如“预览 2028 年秋天的回信”，不能写死为“两年后”。
- **FR-37**：触发后加入两条不同的模拟回答，两条回答的日期都必须落在用户选择的回答时间窗内。
- **FR-38**：模拟回答、模拟用户和预制图片均显示“比赛模拟”或“演示素材”标签。
- **FR-39**：完全自由创建的问题可以正常发布，但第一阶段不会凭空收到未来回答。

## 7. 第一阶段范围

第一阶段必须完成：

- 免注册演示入口；
- 全国发现问题流；
- 手动和模拟行程；
- 城市与时间匹配；
- 创建问题与发布预览；
- 领取、取消和提交现场回信；
- 多次回答时间线；
- 多条满意回答；
- 本地持久化和演示数据重置；
- 一套完整预制故事；
- 移动端适配和可公开访问的 LIVE DEMO。

## 8. 明确不进入第一阶段

- AI 照片比较、AI 回信和聊天；
- 真实后端、数据库和真实用户登录；
- 手机定位、轨迹或现场真实性验证；
- 携程订单或用户行程读取；
- 自由地图搜索和地理编码；
- 视频和录音；
- 微信小程序、Android 或 iOS App；
- 推荐算法、积分、排行榜、私信、支付和打赏；
- 自动照片对齐和差异热力图；
- PWA 离线首次加载能力。

## 9. 第一阶段验收标准

- **AC-01**：首次进入时自动初始化固定的预制场景。
- **AC-02**：没有行程时展示全国问题流，匹配按钮禁用且原因清楚。
- **AC-03**：添加手动行程或模拟行程后，匹配按钮启用。
- **AC-04**：匹配结果只包含同城市且日期重叠的问题，并保持确定顺序。
- **AC-05**：可以使用预制场景完成校验、发布预览和正式发布。
- **AC-06**：未来回信入口显示动态日期，生成的两条模拟回答均位于所选时间窗内。
- **AC-07**：所有模拟行程、回答、用户和素材都有明显标识。
- **AC-08**：可以领取其他用户的问题并取消未完成领取。
- **AC-09**：可以使用预制文字、自写文字或修改预制文字提交回答。
- **AC-10**：未上传照片、未填写文字或未勾选声明时不能提交。
- **AC-11**：提交后立即进入时间线，刷新后仍然存在。
- **AC-12**：回答排序可以在从早到晚和最新优先之间切换。
- **AC-13**：只有问题发起者能标记多条满意回答，且不会删除或阻止其他回答。
- **AC-14**：“我的”能找到当前用户的问题、行程、领取和完成记录。
- **AC-15**：重置后恢复到固定初始数据。
- **AC-16**：约 375px 宽的手机视口可完成全流程，电脑浏览器可操作。
- **AC-17**：页面不直接读取 fixture 或 IndexedDB。
- **AC-18**：TypeScript 类型检查和生产构建通过，控制台无阻塞错误。
- **AC-19**：核心流程不依赖真实后端、真实携程接口、定位或 AI。


## INT-REST-01 真实后端联调（2026-10-02）

用户授权接入同级 backend Java/MySQL 项目，覆盖此前仅 Mock 的限制。保留两个独立仓库；按用户直接指令在当前分支继续，每仓库独立提交，GitHub 操作仅提供命令。

REST 模式使用真实登录、问题、媒体、推荐、领取、坐标签到与回信；Mock 模式保留独立演示数据。REST 不自动制造身份、地点坐标或未来回信。不支持的取消领取、满意标记和演示重置入口隐藏；行程当前仅按用户保存在本机，明确标注，不宣称已同步 MySQL。签到坐标手动输入用于本地联调，不证明真实到场。


### 发布失败反馈（2026-10-03）
发布表单校验失败时必须展示可聚焦的错误摘要和地点字段错误，保留草稿；真实模式在进入预览前检查坐标范围、字符限制和过期日期，不能仅阻止操作而不解释原因。
