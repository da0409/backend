## 1. 本次希望达成什么

目前前端已完成并验收 BASE-02：应用壳、底部导航和发现页静态视觉。DATA-01 与业务页面功能尚未开始，现在统一业务规则，可以减少后续返工。

两份方案的核心概念相近：用户发布地点问题，旅行者领取并提交回信。但是定位签到、匹配规则、回信校验，以及取消领取、满意回答等方面还没有对齐。建议先确认这些业务语义，再分别完善 Mock 和真实后端。

后端可以保留 `capsule`、`reply` 等命名及现有路径。前端通过 REST Adapter 转换命名、响应包装与分页，不要求后端完全照抄前端接口路径。适配层无法补出缺失的业务能力，也无法找回被后端过滤掉的数据。

## 2. 当前前端首版约定

以下是当前仓库已经记录的计划，供双方核对，并非本稿新增要求：

- 首先完成本地 Mock 演示闭环，评委无需注册，流程不依赖真实后端、定位或 AI。
- 没有行程时可浏览全国问题；添加行程后，按同城市、日期重叠进行匹配。
- 创建问题需要标题、描述、参照照片、城市、POI 和回答时间窗；拍摄建议选填。
- 同一问题可被多人领取；用户不能领取自己的问题，同一用户对同一问题最多有一条有效领取。
- 有效领取可以取消，也可以提交回信；回信必须包含照片、文字和现场拍摄声明。
- 同一问题可收到多条回答，时间线默认从早到晚，也可切换为最新优先。
- 问题发起者可以标记或取消标记多条满意回答；满意不会关闭问题或阻止其他人回答。
- 模拟行程和预制未来回信保留在本地，并明确标注演示性质。

依据：PRODUCT 的 FR-01～FR-05、FR-08～FR-09、FR-15～FR-28、FR-33～FR-39；API 的“校验和权限”；TECHNICAL 的“匹配”章节。

## 3. 优先统一的业务差异

### B-01 回信是否必须定位签到

**当前前端约定：**只要求旅行者声明现场拍摄，不采集定位，不声称平台已经验证真实性。

**后端文档：**`POST /tasks/{id}/checkin` 要求经纬度，默认进入地点 300 米范围后变为 `CHECKED_IN`；只有该状态才能调用回信接口。

**影响：**这是流程冲突。若按后端文档执行，前端必须增加定位授权、签到以及拒绝授权或不在现场时的处理，比赛现场也可能无法走通演示。

**建议待确认：**首版允许有效领取直接提交“照片＋文字＋现场声明”；定位签到作为后续可选能力，不作为当前回信前提。若团队选择强制签到，需要先调整产品范围和验收方式，不能由前端伪造坐标绕过。

### B-02 匹配按城市与日期，还是按绕行半径

**当前前端约定：**同城市且日期区间重叠即可入选；同 POI 优先，再结合距离、时间窗中心差、回答数量和稳定 ID 排序。缺少坐标仍可入选。

**后端文档：**`GET /tasks/recommend` 按目的地、日期和绕行半径推荐，`radiusMeters` 默认 3000、最大 10000，按契合度排序。

**影响：**候选范围与排序依据未对齐。若半径是硬过滤条件，同城市内距离较远的问题会被排除，前端重新排序无法恢复这些结果。

**建议待确认：**首版以同城市与日期重叠作为筛选规则；明确日期边界包含关系、缺坐标处理与稳定排序。需要后端说明半径的实际作用，以及城市编码从何处获得。

### B-03 发布与回信的必填规则

**当前前端约定：**发布参照照片必填；回信照片、文字、现场声明全部必填，`onSiteDeclaration` 必须为 `true`。

**后端文档：**创建胶囊的 `mediaList` 选填；提交回信的 `content`、`mediaList` 均选填，没有现场声明字段。

**影响：**可能产生前端产品无法按要求展示的无图问题或不完整回信。只在页面校验不能保证后端数据符合约定。

**建议待确认：**统一前后端校验；明确参照图片与回信图片的选择规则，保存并返回现场声明。首版使用照片和文字，视频、音频不进入本轮前端范围。

### B-04 多条满意回答

**当前前端约定：**问题发起者可以独立标记、取消标记多条满意回答。

**后端文档：**未定义对应操作，也未提供满意状态字段。

**影响：**无法实现满意标记、满意数量和“有满意回答”展示状态。

**建议待确认：**补充设置与取消满意的能力，返回满意状态及所需时间信息；由后端校验操作者是问题发起者。满意操作不改变问题的可回答性。接口路径和字段名可协商。

### B-05 取消领取与领取约束

**当前前端约定：**有效领取可以取消；提交后完成；同一用户对同一问题最多一条有效领取；允许不同用户同时领取。

**后端文档：**有领取、签到、回信，没有取消接口；任务状态包含 `ACCEPTED / CHECKED_IN / COMPLETED / EXPIRED`。

**建议待确认：**补充取消能力及状态语义，说明取消后能否再次领取、重复请求如何处理、能否领取自己的问题、多人领取是否互不排斥。不要把同一用户的领取状态作为整个问题的状态。

### B-06 无行程时的全国发现

**当前前端约定：**没有行程也能浏览固定顺序的全国问题流。

**后端文档：**`GET /capsules` 不传 `creatorId` 默认查询当前用户；`GET /tasks/recommend` 必须传目的地和日期。

**影响：**目前未定义公共发现流的查询方式，不能用“我的胶囊”代替全国发现。

**建议待确认：**增加明确的公共查询入口或查询范围参数，保持排序稳定；列表返回足够的封面、地点、时间窗、作者和回答状态信息。公共浏览是否需要演示会话也应说明。

## 4. 对接前需要补齐的数据约定

| 编号 | 差异或缺项 | 建议确认的内容 |
| --- | --- | --- |
| D-01 | `taskId` 与 `assignmentId` 混用 | 推荐结果、领取结果、我的任务、任务详情中的表格和示例不一致。明确哪一个代表公共任务，哪一个代表某位用户的领取；后续取消、签到、回信分别传哪个 ID |
| D-02 | 问题状态不是同一维度 | 后端 `WAITING / ANSWERED / EXPIRED` 不等同于前端“暂无回答 / 有回答 / 有满意回答”。建议把回答统计与有效期分开定义；明确过期后的操作规则 |
| D-03 | 城市和拍摄建议字段未定义 | 前端需要 `cityCode`、城市名称与可选拍摄建议；后端主要提供 POI、经纬度。明确字段来源，AI 拍摄建议不能替代发布者填写的建议 |
| D-04 | 读取素材时缺少稳定 ID | 上传返回 `mediaId`，但问题详情与回信素材示例只有 URL 等字段。读取结果也应返回稳定 ID；URL 可同时返回供展示，不能用 URL 冒充 ID |
| D-05 | 发现列表数据不足 | 胶囊列表有 `mediaCount`，没有封面素材；部分作者、领取数、满意数等信息缺失。确定列表直接返回哪些字段、哪些通过详情补充，避免每张卡片多次补请求 |
| D-06 | 行程数据归属未明确 | 未定义行程创建、查询和持久化接口。可以首版继续本地保存，也可以后端提供，但要明确责任边界；不能仅有推荐入参就认为行程管理已覆盖 |
| D-07 | 当前用户与“我的回信”缺少明确来源 | 鉴权要求登录后获得 Token，但文档没有登录和当前用户资料接口；回信列表必须传 `capsuleId`，没有明确按当前回答者查询的入口。请补充或说明已有接口 |
| D-08 | 事件时间缺少时区 | 后端日期时间为 `yyyy-MM-dd HH:mm:ss`，前端约定带时区 ISO 8601。建议统一为带偏移的时间字符串；日期窗仍使用 `YYYY-MM-DD`。若保留旧格式，必须声明时区再转换 |
| D-09 | 错误与权限规则不完整 | 请补充业务错误码、HTTP 状态约定、字段错误信息及权限校验规则，便于映射 `ApiError`；精确经纬度的返回对象与访问权限也需说明 |

说明：后端文档写了“已回答的胶囊不能修改”，但没有明确说不能继续收回信。因此本稿不将其判断为“只允许一次回答”，需要双方确认后再确定实现。

## 5. 可由适配层处理的差异

| 差异 | 可行处理 | 注意事项 |
| --- | --- | --- |
| `capsule` / `Question`、`reply` / `Answer` 等命名 | REST Adapter 映射字段与实体 | 先统一含义；尤其不能在含义不明时直接混用任务 ID 与领取 ID |
| `{code,msg,data}` 与前端服务返回值不同 | 适配层拆包，失败转换为 `ApiError` | 需要明确错误码，不建议依赖提示文字判断错误类型 |
| 后端分页、当前前端列表返回数组 | 在适配层聚合分页，或另行确认扩展分页契约 | 不能只取默认前 10 条作为全部结果 |
| 回信列表默认倒序，前端默认正序 | 增加排序参数，或对完整结果排序 | 只反转某一页不能得到完整的最早优先列表 |
| 创建只返回 ID，前端需要完整实体 | 创建后读取详情，或后端直接返回实体 | 需定义后续读取失败时的处理，避免误以为发布失败而重复创建 |
| 后端返回素材 URL，前端实体保存 `assetId` | 适配层管理 ID 到可访问图片的映射 | URL 本身不是冲突，读取接口缺少稳定 ID 才是需要补齐的点 |

另需区分两种时间线：后端 `GET /pois/{id}/timeline` 聚合同一地点下多个胶囊；当前前端问题详情展示同一个问题的多条回答。首版可以使用按 `capsuleId` 查询回信的接口实现，不应直接替换成 POI 聚合时间线。

## 6. 后端文档中的示例与说明待修正项

1. **ID 表格与示例不一致：**领取、我的任务、签到、回信等位置混用 `taskId` 与 `assignmentId`，详见 D-01。
2. **路线距离定义不足：**推荐请求只有目的地 POI 和日期，返回字段却称“与行程路线的顺路距离”。请说明实际是目的地距离，还是另有路线数据来源。
3. **音频上传链路不完整：**上传接口只列图片、视频，回信示例却包含 `AUDIO`。若保留音频能力，需要补上传契约；首版前端可不接入。
4. **人脸模糊示例包含音频：**处理示例出现音频 URL，需要修正素材类型或解释接口语义。
5. **新地点的 POI 来源不明：**创建要求 `poiId`，POI 搜索却描述为只返回已有胶囊的地点。请说明第一次在一个地点发布时如何获得合法 POI。

## 7. 阶段边界与可以保留的后端扩展

建议维持“先完成可演示的 Mock 闭环，再接入真实后端”的当前安排。后端可以继续独立准备扩展能力，但是否纳入首版要由团队明确决定。

- AI 图片对比、拍摄角度建议、人脸模糊、定位签到、视频和音频不是当前前端第一阶段的必做项。
- 创建与回信中的 `blurFace` 默认开启，需要说明实际是否调用 AI、失败是否阻塞提交；当前核心流程不能隐式依赖 AI 服务。
- 预制未来回信不是 AI 生成。`importDemoTrip`、`setActive`、`getActive`、`bootstrap`、`reset`、`revealFutureReplies` 在当前前端契约中属于本地演示控制，不要求真实后端提供同名接口。
- 模拟数据需要明确标识；演示重置只作用于本地演示数据，不应被映射成删除真实业务数据。
- 胶囊编辑、删除、POI 聚合时间线等后端能力可以保留，但不因此追加当前前端页面或业务任务。
- Bearer 鉴权与免注册演示不一定冲突，可以讨论演示会话方案；需要明确会话获取方式，不能直接假定已有可用登录能力。
